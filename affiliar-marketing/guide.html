1. Creating your operator account

1

Visit app.affiliar.co/register and choose Operator Account.

12. Creating a Tiered RevShare plan

Tiered RevShare rewards high-performing affiliates with increasing revenue share percentages based on the NGR they generate.

1

Create a new plan and select "Tiered RevShare"

Go to Commission Plans → + Create Plan → select Tiered RevShare.

2

Define your tiers

Add one or more tiers. Each tier specifies an NGR range and the RevShare percentage for that range.

Tiered RevShare Configuration
TierMin NGRMax NGRRevShare %
Tier 1 €0€5,00025%
Tier 2 €5,001€15,00030%
Tier 3 €15,001Unlimited40%
+ Add Tier

In this example:

  • If an affiliate's players generate €3,000 NGR this month, they earn 25% = €750.
  • If they generate €10,000 NGR, they earn 30% = €3,000.
  • If they generate €25,000 NGR, they earn 40% = €10,000.
How tiers work: The tier is determined by total monthly NGR. The entire commission is calculated at the highest qualifying tier's percentage -- it is not split across tiers. This is simpler for affiliates to understand and more motivating.
Warning: Make sure your tier ranges do not overlap and there are no gaps. The "Max NGR" of one tier should be exactly one cent below the "Min NGR" of the next tier.

Sub-Affiliates

15. What are sub-affiliates and how do they work

Sub-affiliates allow your existing affiliates to recruit new affiliates. The parent affiliate earns an override commission on top of their own earnings, based on the performance of the affiliates they recruited.

Sub-Affiliate Structure
Parent Affiliate (Jane)
Earns own commission + override
recruits
Sub-Affiliate (Tom)
Earns own commission
Sub-Affiliate (Sara)
Earns own commission

In this example:

  • Jane is the parent affiliate. She recruits Tom and Sara.
  • Tom and Sara earn their own commissions based on their plans.
  • Jane earns an override commission -- an additional percentage based on what Tom and Sara generate.
  • The override is paid by the operator, not deducted from the sub-affiliate's earnings.
Important: Sub-affiliates earn their full commission as defined by their plan. The override is an additional cost to the operator -- it does not reduce sub-affiliate earnings.

2

Set the parent affiliate

In the Sub-Affiliate Settings section, use the Parent Affiliate dropdown to select the parent (e.g. Jane).

3

Set the override rate

Enter the override percentage. For example, 10 means the parent earns 10% of the NGR generated by this sub-affiliate's players.

4

Save

Click Save. The relationship is now active. Future commission reports will include the override calculations.

Tip: You can set different override rates for different sub-affiliates under the same parent. This lets you reward top recruiters with higher overrides.

18. How override commission is calculated

Here is a concrete example of how override commission works in a monthly report.

Override Calculation Example

Scenario

  • Parent: Jane (RevShare 30%, override rate: 10%)
  • Sub-Affiliate: Tom (RevShare 25%)
  • Tom's players generated €10,000 NGR this month

Result

  • Tom earns: €10,000 x 25% = €2,500 (his own commission)
  • Jane earns override: €10,000 x 10% = €1,000 (override on Tom's NGR)
  • Jane also earns her own direct commission from her own players separately
Warning: Override commission is calculated on the sub-affiliate's NGR, not on their commission. In the example above, Jane's override is 10% of €10,000 (the NGR), not 10% of €2,500 (Tom's commission).

Campaign Tracking

29. What are campaigns?

A campaign is a tracking metadata identifier — a free-text string that affiliates append to their referral URLs to segment traffic by source. Think of it like UTM parameters: it tells you where the traffic came from so you can compare performance across channels.

Campaigns are not promotional offers, bonuses, or database entities. They are simply labels that flow through the data pipeline:

  1. Affiliate adds a campaign query parameter to their referral link.
  2. Player clicks the link and registers — your platform captures the parameter.
  3. The campaign value is attached to the player and included in every Kafka/REST event.
  4. Affiliar's consumer stores the campaign in ClickHouse.
  5. Reports can be filtered and grouped by campaign to compare traffic source performance.
Why use campaigns? Without campaign tracking, you know which affiliate drove a player, but not how. Campaigns answer questions like: “Does this affiliate's Instagram traffic convert better than their YouTube traffic?”

30. Building tracking links

Affiliates create tracking links by appending query parameters to their referral URL. No configuration is needed — any string passed as the campaign parameter is automatically captured.

URL format

https://yourbrand.com?ref=GYPVCT5M&campaign=instagram_april&sub=story_1
1

Start with the referral link

Copy the base referral URL from the affiliate portal Marketing Tools page (e.g. https://yourbrand.com/?ref=GYPVCT5M).

2

Append a campaign parameter

Add &campaign=your_campaign_name to the URL. Use a descriptive, consistent naming convention (see best practices below).

3

Optionally add sub-source tracking

Add &sub=placement_name to track specific placements within a campaign (e.g. “story_1”, “banner_top”).

If no campaign parameter is provided, the value defaults to an empty string. All events still flow through normally — campaign is purely optional metadata.

31. Tracking parameters explained

The following query parameters are supported on referral links.

ParameterRequiredDescription
ref / affYesAffiliate referral code (e.g. GYPVCT5M)
campaignNoTraffic source identifier (e.g. “instagram_april”, “youtube_review”, “email_blast_q2”)
sub / subIdNoSub-source or placement (e.g. “story_1”, “banner_top”)
clickIdNoUnique click identifier for postback tracking
sourceNoTraffic source category

How campaign data appears in the Kafka event

{
  "affiliate": {
    "affiliateCode": "GYPVCT5M",
    "campaign":      "instagram_april",
    "subId":         "story_1"
  }
}

33. Best practices for campaign naming

Consistent naming makes campaign reports much easier to read and compare over time.

PatternExampleWhen to use
source_monthinstagram_aprilMonthly traffic from a specific platform
platform_typeyoutube_reviewContent format on a platform
channel_quarteremail_blast_q2Quarterly campaigns on a channel
event_namewebinar_launch2026One-off events or promotions
  • Use lowercase and underscores — avoid spaces and special characters.
  • Keep names short but descriptive.
  • Include the time period so you can compare across months or quarters.
  • Use sub / subId for placements within a campaign rather than creating separate campaign names.
Remember: Campaigns are just strings — there is no need to “create” them in advance. Any value passed in the URL is automatically tracked and appears in reports.
Refer-a-Friend

34. What Refer-a-Friend is

Refer-a-Friend is a player-to-player referral program that lives next to your affiliate program. When one of your existing players invites a friend, the friend signs up and deposits, and the inviter (and optionally the friend too) earns a reward.

Affiliar handles all the attribution and qualification work — you only need to configure the reward and the gates, and tell your casino to read from the rewards endpoint when a player visits their “My Rewards” page.

Affiliate vs Refer-a-Friend: Affiliates are marketers (influencers, comparison sites) with commission plans. Refer-a-Friend is for ordinary players inviting friends — a different reward shape, different fraud profile, and a separate ledger. The two systems do not overlap.

35. Enable Refer-a-Friend for a brand

Open Refer-a-Friend → Brand Configs in the operator dashboard. Pick a brand from the list and flip the Enable toggle. Until that is on, every track-signup and track-ftd call from your casino for that brand is rejected with feature_disabled.

Each brand has its own config — you can run different reward formulas, gates, and caps per brand under the same operator account.

Tip: Test on a staging brand first. Once enabled, every new signup with a referral code starts a real PlayerReferral row, and qualified friends start owing real rewards.

36. Configure the reward

The brand config carries three independent reward subdocuments. Only the Referrer reward is required — the other two are optional opt-ins.

RewardPaid toWhenTypical use
ReferrerInviterOn qualificationThanking the player for the lead
RefereeFriend (invitee)On qualification (same moment)Welcome bonus to encourage signup
RecurringInviterMonthly, until staleAfterDaysShare of the friend's ongoing NGR

For each, pick a reward type and an amount:

  • flat — fixed amount in cents, regardless of friend's deposit size.
  • percent_of_ftd — percentage of the friend's first deposit.
  • percent_of_ngr — percentage of the friend's NGR over the period (recurring only).

Also set the currency (rewards are denominated in the operator's base currency by default) and reward kind (cash or bonus — this is a label that flows through to your casino; how you route a “bonus” reward to a bonus wallet is operator-side).

Watch out: The rewardKind field is informational at the data layer. If you want a bonus reward to actually land in a bonus wallet on the player side, your casino backend has to honour the kind when picking which wallet to credit.

37. Set the fraud gates & caps

Refer-a-Friend ships with the same shape of gates as the CPA flow. Before paying out, Affiliar checks that the referral has cleared each gate.

GateWhat it does
Hold periodWait N days after the friend's FTD before paying. Catches early chargebacks.
Minimum wagerFriend must wager at least this much (cumulative since FTD) before qualification.
Stale expiryPending referrals auto-reject after N days — keeps the ledger clean.
Referee is affiliateReject if the friend is also signed up as an affiliate on your platform — affiliate attribution wins.
Monthly capsPer-referrer and per-brand spend ceilings. A referral that would bust either cap is rejected wholesale — no partial payouts.
Tip: Start with conservative gates (e.g. 7-day hold, €25 minimum wager) and loosen them once you have a feel for the chargeback rate on your traffic.

38. Monitor referrals & deliveries

Two activity tables in the operator dashboard track everything:

ViewShowsStatus values
ReferralsOne row per PlayerReferral — the funnel from signup to reward.pending_ftd, pending_qualification, qualified, rewarded, reversed, rejected
Reward LedgerOne row per RewardDelivery — what's owed and what the casino has acked.pending, delivered

Each row drills into a detail view with the full timeline (signup, FTD, qualified, paid) and the configuration snapshot at the moment of qualification, so you can audit exactly which gates and reward formula applied even if the brand config was changed afterwards.

Pending forever? If a reward stays pending in the ledger, it usually means your casino backend hasn't pulled the row yet — the player may not have opened “My Rewards” since qualification. The row will be delivered the next time the casino calls /rewards/claim.

39. Handling chargebacks & reversals

If the friend's FTD is reversed (chargeback, refund, fraud claim), your casino calls POST /api/refer/track-ftd-reversal. Affiliar emits a paired .reversed event for each previously-paid reward — same referralId, opposite sign — and the next pull from /rewards returns them as pending rows. Your casino debits the wallet and acks, same as a credit.

The original PlayerReferral row moves to status reversed and the clawback shows up in the operator dashboard's reward ledger.

Note: If a referral has both referrer and referee bonuses, a reversal claws back both — one debit event for each side.

40. Fixed (per player) commission plan

Pays a fixed amount once per player, in the period that player first crosses every qualification gate you configure. Use this when you want to reward retained players (e.g. $50 once a player has made 3 deposits and earned positive NGR) rather than tie payment to the first deposit alone.

How it differs from CPA

  • CPA: pays per FTD that passes gates at FTD time. A player who deposits once and disappears can still qualify.
  • Fixed: pays per qualified player, evaluated against lifetime cumulative state at period end. Lets you require things FTD time can't satisfy (like "3+ deposits" or "positive lifetime NGR").
  • One-time per player: once a player triggers the Fixed payout, future periods won't pay again for the same player.

Setting it up

  1. Commission → + New Plan opens a dedicated page (not a modal) so you don't lose work to a stray click.
  2. Pick a name, a product (casino / sportsbook / combined), and the Fixed (per player) type.
  3. Set Amount per qualified player (e.g. $50).
  4. Open the Qualification gates and tick what matters: Min FTD deposit, Min deposits count, Hold days, Min lifetime wager, Min wager × FTD, Min cash retained, Min KYC level, Require positive NGR.
  5. Save. The plan slot it occupies depends on the product field — an affiliate can have one casino plan, one sportsbook plan, and one combined plan simultaneously.
What "newly qualified" means: at the end of each Calculate run, the system looks at every player attributed to the affiliate, evaluates all gates against their lifetime metrics, and pays for every player who passes and wasn't already paid in a previous period. The list of paid player IDs is stored on the CommissionReport for cross-period dedupe.
Available from 2-Tier upwards. The tier1 ($53) plan offers RevShare + CPA only; Fixed unlocks at $98 alongside Hybrid and Tiered RevShare.

43. Affiliate wallet setup

Before an operator can pay them, each affiliate sets a USDT-TRC20 wallet address on their profile. Without a wallet, the operator's Pay button stays disabled for that affiliate.

Affiliate-side flow

  1. The affiliate logs into their portal and opens Profile.
  2. In the Payout Wallet card, they paste a TRC20 address (34 characters, starts with T).
  3. Client-side regex + server-side base58 check catch obvious typos before the address sticks.
  4. Once saved, the page shows a green Wallet set badge and the last-updated timestamp.
Double-check the address. Crypto transfers are irreversible. Sans Getirsin doesn't validate the recipient address against the chain — a typo means the funds land in a wrong wallet (if the address even exists).

44. Operator pays affiliates

All affiliate payouts flow through the operator's Sans Getirsin merchant account as USDT-TRC20 transfers. The platform handles the 3-step dance (token → list withdraw accounts → create withdrawal) and matches the callback back to the right payout.

From the Commission page

  1. Calculate & approve commission reports as usual.
  2. Each approved row gets a checkbox. Tick individual affiliates or use the header "select all" to mark every approved one.
  3. Click Pay Selected — a confirmation dialog spells out the total amount and number of affiliates before money moves.
  4. On confirm: for each affiliate, the system bundles all their approved reports into one AffiliatePayout, dispatches it to Sans, and records the provider transaction ID.

From the Payouts page

The Affiliate Payouts sidebar item gives you three tabs:

  • Pending — per-affiliate net payable (gross commission minus what their own subs have already been paid). Pay buttons are gated on wallet presence + the operator's minimum threshold setting.
  • History — every dispatched payout with status (pending, processing, paid, failed, cancelled), Sans transaction ID, and per-row Dispatch / Cancel / Mark-paid actions.
  • Settings — operator-wide minimum payable threshold (affiliates below the floor stay invisible to the Pay flow).
Webhook: Sans posts the result to /api/billing/sans/callback (a single URL covers both deposits and withdrawals — the payload's type field discriminates). On APPROVED the AffiliatePayout flips to paid and every underlying CommissionReport flips to paid along with it.

45. Sub-affiliate payouts

An affiliate can dispatch USDT-TRC20 payments to their own direct sub-affiliates from the Commission → "To my subs" tab. The transfer is funded by the operator's Sans account but accounted against the parent affiliate's internal balance, so the operator never funds the same dollar twice.

Workflow

  1. Sub-affiliate sets their TRC20 wallet on their own profile (same form as a top-level affiliate).
  2. Parent affiliate opens Commission → Sub-Affiliate Payouts → "To my subs" tab — each outgoing payout row shows a Pay button when status is draft or failed.
  3. Clicking Pay opens a confirmation dialog showing the amount and the sub's wallet, then dispatches Sans.
  4. The status walks pending → processing → paid as Sans webhooks the result.
  5. The operator's net to the parent is automatically reduced by every paid/pending sub-payout so they pay only what's left.
Friendly errors: the form translates the raw codes Sans returns into actionable English ("Not enough internal balance", "Sub-affiliate hasn't added a wallet yet", "Provider rejected the transfer — check the wallet address"). Unknown errors fall through verbatim so you can still see Sans's raw message.

46. Internal balance ledger

Every affiliate has a derived ledger that tracks:

  • Earned — sum of approved CommissionReport.totalCents owed to them.
  • Paid to me — sum of AffiliatePayouts they've received (pending + processing + paid all reserve funds).
  • Paid to my subs — sum of SubAffiliatePayouts they've routed downstream.
  • Available = Earned − Paid to me − Paid to my subs. What they can still spend on sub-payouts (or what the operator still owes them in net).

A summary card on the Sub-Affiliate Payouts panel displays all four numbers so the affiliate sees their headroom at a glance. Pay buttons gate on Available ≥ amount — the BE rejects with insufficient_balance if you try to overdraft, and the FE pre-emptively disables the button.

Why this matters: without the ledger an operator could pay an affiliate their full commission, then watch the same affiliate also pay subs out of the operator's Sans balance — double-funding the same commission dollar. The balance check ensures every dollar flows through exactly once.

48. Versioned fees & manual recalculation

Fee configuration is effective-dated. Every save creates a new version with effectiveFrom: now and closes the previous active version's effectiveUntil. The daily fees job picks the version that was active on the day being processed, so historical reports stay frozen and re-running yesterday doesn't apply today's rates retroactively.

What this fixes

  • Before versioning, bumping a fee from 30% to 35% silently rewrote last month's NGR the next time the cron ran. Operators saw past reports shift after the fact.
  • Now: yesterday is yesterday. A re-run produces identical numbers unless you explicitly opt in to retroactive recalc.

Manual recalculation page

The Fees page's Manual fees recalculation card lets you replay the job for any date range:

  • From / To pickers — pick any window up to 90 days. Default is "yesterday only".
  • Re-run N days button — fires the job once per day in the range, using each day's historical fee snapshot.
  • Apply current fees retroactively checkbox — opt-in override that uses today's active fees for past days. Useful when you forgot to update before a rate change went live. A confirmation dialog spells out the trade-off before money numbers move.
History endpoints: the API also exposes GET /api/fees/settings/history and GET /api/fees/provider-rates/history so admin tooling (or curious operators) can see the full version chain — every effective-from timestamp paired with the values that were active.
