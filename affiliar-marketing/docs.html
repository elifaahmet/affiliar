Affiliar Documentation

Affiliar is a multi-tenant affiliate management platform built for iGaming operators. It handles everything from affiliate onboarding and referral tracking to commission calculation and payment workflows.

What to decide, what you need, in what order

Planning your integration

Affiliar sits beside your platform: your system stays the source of truth for players and money, and tells Affiliar what happened. Everything else — attribution, commission, payouts, reporting — is derived from that stream. Getting the stream right is the whole integration; the rest is configuration in the dashboard.

What you need before you start

ValueWhere it comes fromUsed for
tenantIdYour operator record in AffiliarEvery event — which operator the activity belongs to
brandIdThe brand under that operatorEvery event — one operator can run several brands
CredentialsA Kafka SASL user, or an operator JWT for RESTAuthenticating the stream

Send these exactly as issued. A wrong tenantId does not raise an error — the event is attributed elsewhere or dropped, and the first sign of trouble is a report that never fills up. Confirm the first few events land before wiring the rest.

Kafka or REST?

KafkaREST
Best forContinuous production trafficLow volume, backfills, getting started
DeliveryBuffered and retried by the brokerYour code owns the retry
If Affiliar is unreachableEvents wait in the topicYou must queue them yourself
SetupBroker credentials, a topic, TLSAn HTTP call

Both accept the same event shape, so starting on REST and moving to Kafka later costs nothing — the payloads do not change.

The order that works

  1. Registrations first. player.registered carries the referral code and is what creates the attribution. A deposit for a player Affiliar has never seen cannot be credited to anyone, and sending it later will not fix the reports in between.
  2. Then money. wallet.deposit.confirmed with isFirstDeposit set correctly — FTD counts and CPA qualification both hang off it.
  3. Then play. Bets and wins, which produce GGR and therefore RevShare.
  4. Then the rest. Withdrawals, bonuses, corrections and fees refine NGR, but nothing depends on them being there from day one.

Use each event's real timestamp in occurredAt, not the time you send it. Reports bucket by that field, so replaying history with today's date collapses months of activity into a single hour.

Testing before you go live

Every event carries an eventId you choose and duplicates are rejected, so replaying a batch is safe while you get it right. Send a handful of registrations, confirm they appear against the right affiliate under Players, then let the rest follow. If they arrive unattributed, the referral code in the payload is the first thing to check.

Core Concepts

Understanding the data model before you integrate.

Operator

The iGaming company using Affiliar. Each operator has their own isolated tenant, affiliates, plans, and reports.

Affiliate

A partner who drives player registrations. Each affiliate has one or more referral codes and is assigned a commission plan.

Referral Code

The token embedded in player registration links (e.g. ?ref=GYPVCT5M). Used to attribute players to affiliates. One affiliate can have multiple codes.

Commission Plan

Defines how an affiliate earns money — RevShare, CPA, Hybrid or Tiered. Assigned per affiliate; falls back to the operator default.

Commission Report

One report per affiliate per calendar month. Calculated on demand; follows an approval workflow before payment.

Kafka Integration

The recommended integration for high-volume, real-time iGaming platforms.

Topic naming: produce to igaming.player.events (configurable). Partition by tenantId for ordering guarantees per operator.

Message format

{
  "eventId":   "uuid-v4",           // required — used for deduplication
  "eventType": "registration",      // registration | deposit | round | withdrawal
  "tenantId":  "operator_object_id", // your operator _id
  "timestamp": "2026-04-06T10:00:00Z",
  "affiliate": {
    "affiliateId":   "user_object_id",  // preferred — User._id
    "affiliateCode": "GYPVCT5M",        // fallback if affiliateId unknown
    "campaign":      "instagram_april", // optional — tracking metadata
    "subId":         "story_1"          // optional — sub-source
  },
  "player": {
    "playerId": "player_001",
    "brandId":  "brand_123"          // optional
  },
  "data": {
    "amountCents": 5000,             // for deposit / round events
    "currency":    "EUR"
  }
}

Consumer behaviour

  1. Validates schema with Zod — malformed messages go to a dead-letter topic.
  2. Checks inbox for duplicate eventId — skips if already processed.
  3. Resolves affiliateId from affiliateCode if not provided (cached in memory).
  4. Upserts an hourly bucket in affiliar.activity_hourly (ClickHouse).
  5. Marks the inbox entry as processed.

Event Schema

Every event shares the same envelope — eventId, eventType, tenantId, brandId, playerId, currency, occurredAt, source, data. The table below lists each supported eventType and the fields you must set inside data. All monetary fields are integer cents — never floats.

NGR Formula

Commission plans run on Net Gaming Revenue. Affiliar computes it from the delta columns written by every event: 

GGR = (bets − bet_rollbacks) − (wins − win_rollbacks)

NGR = GGR
    − bonus_issues
    − chargebacks
    − corrections_down   (casino gifted money)
    + corrections_up     (casino recovered money)
    − additional_deductions
    − casino_taxes
    − payment_system_fees
    − jackpot_fees
    − game_provider_fees

All components are summed over the period + affiliate + brand + currency + provider you're reporting on. Per-provider GGR/NGR is exact because providerId is part of the sort key — matched bets and wins always collapse to the same row.

Fees & Adjustments

Four fee buckets feed into NGR. For each one you pick a source — do not mix them within the same bucket or you'll double-count.

BucketOption 1 — You pushOption 2 — Affiliar computes
Payment systempaymentSystemFeesCents on fees.daily.adjustment% of deposits (operator or brand scope)
JackpotjackpotFeesCents% of bets
Casino taxcasinoTaxesCents% of GGR
Game providergameProviderFeesCents% of provider GGR, per providerId

Percentages are configured in the operator dashboard under Fees. Each setting can be operator-wide (applies to every brand) or brand-specific (overrides the default for that brand only).

Affiliar's daily job reads yesterday's activity from ClickHouse, resolves the right rate per (brand, provider), and writes fee rows back to the delta table. Fee rows use player_id = "__fees__" so they stay out of per-player reports while still feeding NGR.

Multi-Currency

Every event carries its native currency (ISO 4217, or an empty string for events like player.registered where no wallet exists yet). The consumer normalizes each monetary field to the tenant's reporting currency (USD by default) before writing to ClickHouse, using rates refreshed daily from the European Central Bank via frankfurter.app.

The native currency value is preserved on the delta row so per-currency breakdowns are still possible — just GROUP BY currency in reports. Summed totals across the whole view are in the reporting currency; per-currency totals are in native cents.

Supported currencies default to USD, EUR, TRY, GBP, INR, JPY. Extend via FX_SUPPORTED_CURRENCIES on the affiliate-be deployment.

Idempotency

Every event must include a unique eventId. Affiliar stores processed IDs in an inbox collection and silently ignores duplicates. This means:

  • It is safe to retry failed requests without double-counting.
  • Kafka at-least-once delivery is handled automatically.
  • Use a UUID v4 or a stable hash of your internal transaction ID.
Do not reuse event IDs across different events even if they have different content — the second event will be silently dropped.

Managing Affiliates

Affiliates can be created individually, bulk-imported via CSV, or invited to self-register.

Creates a pending account. The affiliate must activate it via the link you share.

  "name":     "Jane Doe",
  "mobileNumber":     "+905550000000",   // optional
  "referralCodes":    ["LEGACY_CODE"]    // optional legacy codes

Send up to 500 affiliates in one request. Returns per-row success/failure.

POST /api/affiliates/bulk

[

  { "email": "b@x.com", "username": "aff2", "name": "Aff Two" }
]

Self-registration

Share your operator invite link. Affiliates register themselves and are immediately active.

https://app.affiliar.co/register?operatorId=<your_operator_id>

Referral Codes

Each affiliate gets an auto-generated 8-character code (e.g. GYPVCT5M). Additional legacy codes can be attached at creation time.

Player registration links should pass the code as the ref query parameter:

https://yourcasino.com/register?ref=GYPVCT5M

When a player event arrives with an affiliateCode, Affiliar looks it up in AffiliateProfile.referralCodes and resolves the owner. All subsequent events from that playerId are attributed to the same affiliate.

Sub-Affiliates

Affiliar supports a 2-level affiliate hierarchy. A parent affiliate earns an override commission on their sub-affiliates' NGR.

Max depth is 2 levels. A parent affiliate cannot itself have a parent. This is enforced at both registration and via the operator API.

Assign a parent via operator dashboard

PATCH /api/affiliates/:id/parent

{
  "parentAffiliateId": "user_object_id",
  "overrideRate":      10   // 10% of sub's NGR goes to parent
}

Sub-affiliate self-registration

Affiliates can recruit sub-affiliates via a recruit link that includes their referral code as parentCode:

https://app.affiliar.co/register?parentCode=GYPVCT5M

On registration, Affiliar automatically resolves the parent affiliate, validates the depth limit, and sets the parentAffiliate link.

List sub-affiliates

GET /api/affiliates/:id/sub-affiliates

Override commission calculation

When monthly commission reports are calculated, the engine:

  1. Calculates each affiliate's direct commission (RevShare / CPA / etc).
  2. For each sub-affiliate with a parent and overrideRate > 0, computes floor(max(0, subNgrCents) × overrideRate / 100).
  3. Adds this to the parent's overrideCents and totalCents.
  4. Creates a zero-direct parent report if the parent had no player activity that month.

Commission Plans

Plans define how affiliates earn. One plan is marked as the operator default; individual affiliates can be assigned a different plan at any time.

POST /api/commission/plans

{
  "name":      "Standard RevShare",
  "type":      "revshare",       // revshare | cpa | hybrid | tiered_revshare
  "isDefault": true,
  "revshare":  { "rate": 30, "basis": "ngr" }
}

RevShare

The affiliate earns a fixed percentage of NGR (Net Gaming Revenue) or GGR (Gross Gaming Revenue) each month.

{
  "type":     "revshare",
  "revshare": {
    "rate":  30,     // percentage (0–100)
    "basis": "ngr"  // "ngr" or "ggr"
  }
}

Commission = ngrCents × rate / 100

CPA — Cost Per Acquisition

A fixed payout for each qualifying First-Time Depositor (FTD).

{
  "type": "cpa",
  "cpa":  {
    "payoutCents":     5000,  // €50.00 per qualifying FTD
    "minDepositCents": 2000   // minimum deposit to qualify (optional)
  }
}

Commission = ftdCount × payoutCents

Hybrid

Combines both RevShare and CPA in a single plan.

{
  "type":     "hybrid",
  "revshare": { "rate": 20, "basis": "ngr" },
  "cpa":      { "payoutCents": 3000 }
}

Commission = (ngrCents × rate / 100) + (ftdCount × payoutCents)

Tiered RevShare

The RevShare rate increases as the affiliate's monthly NGR crosses defined thresholds. The applicable tier is determined each month independently.

{
  "type": "tiered_revshare",
  "tiers": [
    { "minNgrCents": 0,      "maxNgrCents": 500000,  "rate": 25 },
    { "minNgrCents": 500001, "maxNgrCents": 2000000, "rate": 32 },
    { "minNgrCents": 2000001,"maxNgrCents": null,     "rate": 40 }
  ]
}
Set maxNgrCents: null on the last tier to make it open-ended. Gaps between tiers are allowed — NGR in a gap earns 0%.

Override Commission

When a sub-affiliate generates NGR, their parent earns an additional percentage on top of their own commission. This is funded by the operator — the sub-affiliate's earnings are unaffected.

FieldDescription
overrideRate% of sub's NGR that flows to parent. Set by operator per sub-affiliate (0–100).
overrideCentsTotal override earned in the report period.
directCentsCommission from the parent's own player activity.
totalCentsdirectCents + overrideCents

Commission Reports

One report is generated per affiliate per calendar month. Reports are not created automatically — trigger calculation via the API or dashboard.

POST /api/commission/reports/calculate

{
  "year":  2026,
  "month": 4    // 1–12
}

This calculates reports for all affiliates in your operator account for the given month. Existing draft or pending_approval reports are overwritten. approved and paid reports are protected.

Campaign Tracking

A campaign is a tracking metadata identifier — a free-text string that affiliates append to their referral URLs to segment traffic sources. It is not a promotional offer or a database entity; it is simply a label that flows through the data pipeline and enables campaign-level reporting.

Tracking URL format

https://yourbrand.com?ref=GYPVCT5M&campaign=instagram_april&sub=story_1

Tracking parameters

ParameterRequiredDescription
ref / affYesAffiliate referral code (e.g. GYPVCT5M)
campaignNoTraffic source identifier (e.g. “instagram_april”, “youtube_review”, “email_blast_q2”)
sub / subIdNoSub-source or placement (e.g. “story_1”, “banner_top”)
clickIdNoUnique click identifier for postback tracking
sourceNoTraffic source category

How it flows

  1. Affiliate adds campaign parameter to their referral URL.
  2. Player clicks the link and registers — your platform captures the query parameters.
  3. The campaign value is attached to the player record and included in every Kafka/REST event.
  4. The Affiliar consumer stores the campaign field in ClickHouse's activity_hourly table.
  5. Reports can be filtered and grouped by campaign to compare traffic source performance.

Kafka event with campaign field

{
  "affiliate": {
    "affiliateCode": "GYPVCT5M",
    "campaign":      "instagram_april",
    "subId":         "story_1"
  }
}
If a referral link does not include a campaign parameter, the value defaults to an empty string. All events still flow through normally — campaign is purely optional metadata.

Click Tracking & Smartlinks

A smartlink routes a visitor through Affiliar before sending them on to the brand, so the click is recorded at the top of the funnel. This turns reporting from “registrations onward” into a full clicks → registrations → FTD funnel with real conversion rates — and attaches a unique click_id the affiliate gets back on every postback.

Smartlink format

https://app.affiliar.co/api/r/<code>?sub=fb_ad_42&campaign=instagram_april&to=https://brand.com/promo
PartRequiredDescription
/api/r/<code>YesThe affiliate's referral code (per brand).
subNoThe affiliate's own click/player reference (echoed back as click_id/sub_id).
campaignNoTraffic-source label, recorded on the click.
toNoLanding-page override. Honoured only when it points at the brand's own host (no open redirect); otherwise the brand's default URL is used.

Affiliates don't build this by hand — the portal's Marketing Tools generate the smartlink (and saved links expose it as trackingUrl).

How it flows

  1. Visitor clicks the smartlink. Affiliar records a Click (code, brand, sub, campaign, country, IP/UA) and mints a unique click_id.
  2. Affiliar 302-redirects to the brand landing with ?affiliate=<code>&click_id=<id>&sub=… appended.
  3. On registration the casino echoes click_id back in the player.registered event — the matching click is marked converted (exact click→registration attribution).
  4. Dashboards and campaign reports show Clicks, Click→Reg % and Reg→FTD % for both affiliates and operators.
Bot filtering: link-preview bots, crawlers and CLI fetchers (and requests with no user-agent) are flagged and excluded from funnel counts, so conversion rates aren't inflated — they're still recorded and still redirected. The attribution window is 30 days. See also Postback for how click_id is returned to the affiliate.

Refer-a-Friend

A player-to-player referral engine sits next to the affiliate program. Where the affiliate program tracks marketers, Refer-a-Friend tracks players inviting other players — separate config, separate fraud gates, separate payout ledger.

The delivery model is pull-on-demand: Affiliar holds qualified rewards in a per-player ledger, and your casino backend reads from /api/refer/player/<id>/rewards whenever a player opens their "My Rewards" page. No webhook endpoint to host, no retry queue to monitor — the casino is in control of when it credits the wallet, and idempotency is guaranteed by an explicit ack step. If you would rather be pushed to than poll, you can enable a reward webhook per brand; it runs alongside the pull ledger rather than replacing it.

  • Per-brand config — every brand under your operator can have its own enable flag, reward formula, gates, and caps.
  • Two-sided rewards — pay the inviter plus an optional welcome bonus to the friend at qualification.
  • Recurring NGR share — keep paying the inviter a slice of the friend's NGR each month, capped by config.
  • Fraud gates — hold period, wager threshold, monthly spend caps, stale-referral expiry.
  • Chargeback reversal — if the friend's FTD reverses, Affiliar emits a paired .reversed event so the casino can debit the wallet back.

Config & Reward Types

Each brand has its own ReferAFriendConfig document. Manage it via the operator dashboard or directly via PUT /api/refer/config/:brandId.

Reward formula

Three reward subdocuments — referrer (always required), referee (optional welcome bonus), and recurring (optional monthly NGR share). All three accept the same shape:

{
  "enabled":    true,
  "rewardType": "flat" | "percent_of_ftd" | "percent_of_ngr",
  "amountCents": 500,         // for "flat"
  "percent":     10,          // for percent_* types (0–100)
  "currency":    "EUR",
  "rewardKind":  "cash" | "bonus"  // FE label only — wallet routing is operator-side
}

Qualification gates

{
  "holdDays":           7,    // wait this many days after FTD before paying
  "minWagerCents":      2500, // friend must wager this much before qualification
  "staleAfterDays":     30,   // pending referrals auto-expire after N days
  "refereeIsAffiliate": "reject" // reject if friend is also signed up as an affiliate
}

Monthly caps

{
  "caps": {
    "perReferrerCentsMonthly": 10000, // max paid to one referrer per month
    "perBrandCentsMonthly":    500000 // hard ceiling for the brand
  }
}

A referral that would push past either cap is rejected wholesale — no partial payouts. Cleaner audit story than picking a winner.

Three write endpoints (your casino calls these) plus two read endpoints (your casino polls these). All require an operator JWT; scope is resolved from the token.

Call when the referred friend makes their first deposit. Affiliar runs the qualification gates here.

GET /api/refer/stats?playerId=<p_…>&brandId=<optional>

Returns a per-player summary: how many friends they've invited, status breakdown, total earned, plus an asReferee block if this player was themselves invited by someone else.

Pull & Claim Flow

When a player opens their "My Rewards" page on the casino, your backend polls Affiliar for any owed rewards, credits the wallet for each, then acks. The ack flips the row from pending to delivered on Affiliar's side so the same reward isn't returned twice.

1. Read the ledger

GET /api/refer/player/<playerId>/rewards
Authorization: Bearer <operator-jwt>

// response
{
  "pending": [
    {
      "id":             "d_8a3f…",
      "eventType":      "referral.reward.issued",
      "referralId":     "r_492a…",
      "rewardCents":    500,
      "rewardCurrency": "EUR",
      "rewardKind":     "bonus"
    }
  ],
  "history": [ /* last 20 delivered rows */ ]
}

2. Credit + ack

For each pending row, the casino picks a wallet matching rewardCurrency, credits (or debits for .reversed events) the amount, then posts the ids back:

POST /api/refer/player/<playerId>/rewards/claim
{
  "ids": ["d_8a3f…", "d_c01d…"]
}

// response
{
  "claimed": ["d_8a3f…", "d_c01d…"],
  "skipped": []  // rows already delivered or not owned by this operator
}

If the ack fails (network blip), the row simply reappears as pending next call. Your wallet idempotency should make the credit retry safe — Affiliar guarantees no row will be marked delivered without an explicit ack.

Per-friend listing

If you want to render a table of "people I invited and what I earned from each," call:

GET /api/refer/player/<playerId>/referrals

Returns one row per PlayerReferral where this player is the referrer, with status, the matching pendingDeliveryId (so an inline Claim button can pass it straight to /rewards/claim), and reward amount / kind.

Reward Webhook

Optional push delivery, configured per brand in Refer-a-Friend → [Brand] → Reward webhook. When enabled, Affiliar POSTs each reward event to your HTTPS endpoint as it happens instead of waiting for you to poll.

It does not replace the pull ledger. Both paths read the same delivery rows, and whichever one lands first settles the reward and runs the state cascade. Enabling a webhook cannot double-credit a player, and if your endpoint is down the rewards simply stay claimable through /rewards/claim as before.

Setup

  1. Enter your HTTPS endpoint and tick Deliver reward events to this endpoint.
  2. Copy the signing secret shown on save — it is displayed once and never retrievable afterwards. Only the last four characters are shown from then on.
  3. Use Send test event to verify your handler before real traffic arrives. Test payloads carry "test": true and are never recorded.

Verifying the signature

Every request carries these headers:

HeaderMeaning
X-Affiliar-EventEvent type — branch on this.
X-Affiliar-DeliveryUnique per attempt. Dedupe on the event id, not this.
X-Affiliar-TimestampUnix seconds. Reject anything older than 5 minutes.
X-Affiliar-Signaturet=<ts>,v1=<hex> — HMAC-SHA256, see below.

Affiliar signs <timestamp>.<raw-body> with your secret. Compare against the raw request bytes, before any JSON parsing — re-serializing the body will change the digest.

import hmac, hashlib, time

def verify(headers, raw_body, secret, max_age=300):
    parts = dict(p.split("=", 1) for p in headers["X-Affiliar-Signature"].split(","))
    ts = int(parts["t"])
    if abs(time.time() - ts) > max_age:
        raise ValueError("stale event")

    expected = hmac.new(secret.encode(),
                        f"{ts}.{raw_body}".encode(),
                        hashlib.sha256).hexdigest()

    # More than one v1= may be present during a secret rotation —
    # accept the request if ANY of them matches.
    sent = [v for k, v in (p.split("=", 1) for p in
            headers["X-Affiliar-Signature"].split(",")) if k == "v1"]
    if not any(hmac.compare_digest(expected, s) for s in sent):
        raise ValueError("signature mismatch")

Rotating the secret

Hit Rotate to mint a new secret. The previous one keeps signing for 48 hours, and during that window each request carries two v1= values — one per live secret. That is why your verifier must accept any match: it lets you deploy the new secret without a coordinated cutover and without dropping in-flight retries.

Retries

Respond 2xx to acknowledge. Anything else — including a timeout after 10s — is retried on this schedule:

immediate → 1m → 5m → 30m → 2h → 12h → 24h

After the last attempt the delivery is marked failed. The reward is not lost — it stays in the ledger, and you can re-queue it with the Retry button on the reward ledger table. Answer fast and do your work asynchronously; a slow handler will time out and be retried, which your idempotency check must absorb.

Payouts via Coinflux

Affiliar dispatches stablecoin transfers to affiliates and sub-affiliates through Coinflux. Coinflux is non-custodial: it is the approval desk and the record, not a wallet. Affiliar opens a withdrawal request, the operator approves it in the Coinflux dashboard and pays from their own funds, and a signed webhook reports the outcome. No key or balance of yours ever sits at the provider.

FlowFunded byTracked on
Operator → AffiliateOperator's own fundsAffiliatePayout
Affiliate → Sub-affiliateOperator's own funds (debited from the affiliate's internal ledger)SubAffiliatePayout
Operator → Affiliar (subscription)Operator's own fundsBillingTransaction

Affiliates and sub-affiliates are not Coinflux tenants — they are end users with a stablecoin wallet, so every outbound transfer originates from the operator's own funds. Affiliar keeps an internal balance ledger so the same commission dollar is never funded twice.

USDC has no Tron contract, which is why TRC20 is USDT-only — the portal will not offer that pair. Defaults are TRC20/USDT, so an affiliate who set their wallet before the other chains existed keeps working untouched. Before a transfer is dispatched Affiliar re-checks both the network/asset pair and that the address shape matches the chain; funds sent to the wrong chain do not come back.

Dispatch

Both AffiliatePayout and SubAffiliatePayout use the same withdrawal call.

POST {COINFLUX_API_URL}/withdrawals
  X-Api-Key: {COINFLUX_API_KEY}

  {
    "playerId":  "<affiliateId>",   // a label: who this payout is for
    "amount":    78.12,               // whole token units, 8dp
    "address":   "0x…",               // the affiliate's payout wallet
    "currency":  "USDC",              // USDT | USDC
    "network":   "ERC20",             // TRC20 | ERC20 | BEP20
    "reference": "<payoutId>"       // our row id, echoed back on the webhook
  }

→ { "withdrawalId": "…", "status": "pending" }

The returned withdrawalId is stored on the row as providerTransactionId and the payout moves to processing until the webhook arrives. amountCents is USD-pegged fiat cents; every asset paid in is a USD stablecoin, so the conversion is 1:1 (amountCents / 100) whether it is USDT or USDC.

Webhook

One signed callback reports the outcome of every withdrawal. reference is the primary match key on the way home.

POST /api/billing/coinflux/callback
  X-Signature: HMAC-SHA256 over the raw body, keyed with COINFLUX_WEBHOOK_SECRET

  {
    "withdrawalId": "…",
    "reference":    "<payoutId | subPayoutId>",
    "status":       "completed",   // or failed / rejected
    "txHash":       "0x…"
  }

A bad or missing signature is rejected and logged as affiliate.payout.coinflux.bad_sig — the payout is left untouched rather than trusted. The handler matches SubAffiliatePayout first, then AffiliatePayout. On success the row flips to paid and a top-level affiliate payout propagates paid to every CommissionReport in sourceReportIds; on failure it flips to failed with the provider reason. Re-deliveries are idempotent — terminal statuses do not re-flip.

Reminders & suspension

A daily job emails every operator user on a fixed cadence around the due date. Each stage fires once per billing cycle, on the calendar date itself regardless of what time the job runs.

WhenStage
7, 5, 3 and 1 days beforeUpcoming renewal
Due datePayment due today
1, 3, 5 and 7 days afterOverdue, counting down to suspension
10 days afterSuspended

Suspension closes the operator panel. Affiliates are cut off from reports, links and creatives too, but keep access to their balance, payout history and payout wallet — they did not fail to pay, and commission already earned is theirs regardless.

While suspended, no activity is recorded. Clicks, registrations, deposits and player activity occurring during suspension are not captured and cannot be reconstructed once service resumes, so commission for that period cannot be calculated either. Everything recorded up to the suspension date is preserved, and paying restores access immediately — but only from the payment date onward.

Late interest

Interest accrues daily on an overdue invoice, derived from a published benchmark rather than a flat number:

daily % = (SOFR annual % + margin %) / 365

SOFR is the US overnight funding rate published each business day by the New York Fed; Affiliar refreshes it on a timer so an overdue invoice is charged against a current rate. The margin defaults to 8%, the middle of ordinary commercial terms. At a SOFR of 3.63% that is roughly 0.032% per day — about $3 on a $935 invoice left unpaid for ten days.

Every overdue email states the rate, the benchmark it sits on, the margin and the date SOFR was read, so the figure can be checked rather than taken on trust. If the benchmark cannot be fetched the last known value stands.

Real-time Postback (S2S)

Affiliates can receive a server-to-server callback the moment a conversion happens, keeping their own tracker in sync without polling. Configure it in the portal under API Access → Real-time Postback: set a URL template with {macros}, pick which events fire, and toggle it on. On each enabled conversion Affiliar sends an HTTP GET to the URL with the macros filled, retrying with exponential backoff (up to 5 attempts) on non-2xx responses.

GET /api/affiliate-portal/postback Current config + supported events & macros
PATCH /api/affiliate-portal/postback Set URL, events, on/off
GET /api/affiliate-portal/postback/deliveries Recent delivery log (status, HTTP code)

Matching players to your own IDs

You don't need our player ids to reconcile conversions — use sub as the bridge. Put your own click/player reference in the sub parameter of your tracking link (?affiliate=CODE&sub=<your-id>); we store it and return it on every postback as {click_id} / {sub_id}. Each postback also includes our {player_id}, so you can persist the mapping from the first callback. In the portal the value shows on the Players page as Your reference, and you can set or override it per player there (or via PATCH /api/affiliate-portal/players/:playerId/ref) if you couldn't pass a sub at click time. The same field is returned by GET /players on the pull API.
