# Refer-a-Friend — Outbound Webhook Contract

This document is for the operator's backend team integrating Affiliar's Refer-a-Friend reward webhook. When a player-referral qualifies, Affiliar POSTs a signed payload to your endpoint. Your job is to credit the referrer's wallet/bonus balance and respond with `2xx`.

## 1. Configuration

Configure your webhook in **Affiliar → Settings → Refer-a-Friend → [Brand] → Webhook**:

- **URL** — your HTTPS endpoint, e.g. `https://api.your-casino.com/internal/affiliar-rewards`
- **Secret** — generated by Affiliar, revealed once at creation; store securely on your side, used to verify request signatures

You can rotate the secret at any time. The new secret begins signing immediately; in-flight retries use the secret valid at delivery time.

## 2. Request format

```http
POST {your-webhook-url}
Content-Type: application/json
User-Agent: Affiliar-Webhooks/1.0
X-Affiliar-Event: referral.reward.issued
X-Affiliar-Delivery: 8b3e9d2a-7c1f-4d83-9b6e-2a4f1c8d9e7b
X-Affiliar-Timestamp: 1746611820
X-Affiliar-Signature: t=1746611820,v1=5257a869e7ecebeda32afb5cb1dd2b1f9d6f54b08b29c8ccb3fb...

{
  "id": "evt_01HK4P9X8ZG7MQ2VBNT3WD6YA1",
  "type": "referral.reward.issued",
  "createdAt": "2026-05-07T11:30:20.000Z",
  "data": {
    "brandId": "65b4...",
    "referralId": "65f7...",
    "referrerPlayerId": "p_842931",
    "refereePlayerId": "p_991042",
    "rewardCents": 500,
    "rewardCurrency": "EUR",
    "rewardKind": "bonus",
    "qualifiedAt": "2026-05-07T11:30:19.412Z",
    "ftdCents": 5000,
    "ftdCurrency": "EUR"
  }
}
```

### Headers

| Header | Description |
|---|---|
| `X-Affiliar-Event` | Event type. Phase 1 ships exactly one: `referral.reward.issued`. |
| `X-Affiliar-Delivery` | Unique per delivery attempt. **Use this for idempotency.** Same event id may appear with different delivery ids on retries — dedupe by event `data.referralId` plus `id`. |
| `X-Affiliar-Timestamp` | Unix timestamp (seconds) used in the signature. Reject events with timestamps older than 5 minutes to prevent replay. |
| `X-Affiliar-Signature` | HMAC-SHA256 signature, see §3. |

## 3. Verifying the signature

Affiliar signs `<timestamp>.<raw-body-utf8>` with the brand's webhook secret using HMAC-SHA256. Multiple `v1=` values may appear (during secret rotation); accept the request if **any** signature matches.

Pseudo-code:

```python
import hmac, hashlib

def verify(headers, raw_body, secret, max_age_seconds=300):
    sig_header = headers["X-Affiliar-Signature"]                   # "t=…,v1=…"
    parts = dict(p.split("=", 1) for p in sig_header.split(","))
    timestamp = int(parts["t"])
    received  = parts["v1"]

    if abs(time.time() - timestamp) > max_age_seconds:
        raise ValueError("timestamp too old, possible replay")

    signed_payload = f"{timestamp}.{raw_body.decode('utf-8')}"
    expected = hmac.new(secret.encode(), signed_payload.encode(), hashlib.sha256).hexdigest()

    if not hmac.compare_digest(expected, received):
        raise ValueError("signature mismatch")
```

`hmac.compare_digest` (or your language's constant-time comparator) is required. Do not use `==` on the hex digests.

## 4. Expected response

Affiliar treats any `2xx` as successful delivery. Do all your work synchronously if you can finish in under 10 seconds; otherwise enqueue and `202 Accepted` immediately.

| Response | Affiliar behaviour |
|---|---|
| 2xx | Delivery is `delivered`. No retries. |
| 408, 429, 5xx | Retried per §5 schedule. |
| 4xx (other than 408, 429) | Marked `failed` immediately, no retries. Surfaced in the operator dashboard for manual `Replay`. |
| Timeout (>10s) | Counted as failure, retried. |

Treat 4xx returns as a contract bug — Affiliar will pause and require manual review, not back off and try again. If your endpoint can return early-rejection 4xx for legitimate reasons (player not found, brand offline), use 2xx with an internal log instead, then handle the rejection out-of-band.

## 5. Retry schedule

```
attempt   delay-from-previous   cumulative-elapsed
1         immediate              0
2         1 minute               1m
3         5 minutes              6m
4         30 minutes             36m
5         2 hours                2h36m
6         12 hours               14h36m
final     24 hours               38h36m
```

After 6 unsuccessful attempts, delivery is marked `failed`. The reward is not lost — operators can replay any failed delivery from the dashboard or via the admin API.

## 6. Idempotency

Affiliar guarantees at-least-once delivery per qualified referral. Dedupe on the operator side by `data.referralId` (or `id`); both are stable across retries.

A single `referralId` will never appear in more than one `referral.reward.issued` event. If you see two with the same `referralId`, the second is a duplicate — return 2xx without re-crediting.

## 8. Operations

- **Replay** — operator dashboard surfaces every `failed` delivery with a Replay button. Replay creates a new `RewardDelivery` row with attempt counter reset.
- **Pause** — toggling `webhook.enabled = false` stops all further deliveries to your endpoint without losing pending events; they remain `pending` until you re-enable.
- **Inspect** — every delivery's response code, body snippet (first 256 chars), and latency are visible in the dashboard for the last 30 days.

## 9. What we do NOT send

- Personal data beyond opaque player ids
- KYC documents
- Operator credentials
- Anything in the `Player` collection (Affiliar doesn't even own that data; player ids are operator-scoped strings)

## 10. Versioning

This contract is `v1`. Future versions will:

- Use a new event type (e.g. `referral.reward.issued.v2`)
- Be opt-in via a per-brand `webhookVersion` setting
- Maintain `v1` payloads at the same URL until you migrate

We will never silently change the shape of a `v1` payload.
